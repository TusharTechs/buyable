Live Deployed on AWS, running against real storefronts

Every tool tells you how many rules your site breaks. None of them tell you whether anyone can actually buy.

Buyable takes a real revenue journey, a checkout, a booking, an application, and attempts it three times over: as someone using a screen reader, as an AI shopping agent, and as a sighted customer with a mouse. It reports one number. When a journey cannot be completed, it finds the element responsible, writes the patch, and re-runs the journey against a build containing that patch to prove the fix works.

Worked example

A worked example

This is a real run against a live storefront with one deliberate defect: the pay button is an icon-only button whose only content is an aria-hidden icon, so it has no accessible name. A rule scanner reports it as one low-severity item among dozens. Measured by task completion it is total. Three attempts per persona, because a single run of anything stochastic proves nothing. One baseline attempt hit a network error and was excluded from the denominator rather than counted against the site, which is why the control reads two of two.

The baseline control completed this journey every time. The site is the variable, not the model. That control is what separates a measurement from an accusation.

One missing attribute, and two revenue channels close at once. Neither the screen reader user nor the AI agent could establish what the control does, and neither could complete the purchase.

What an agent does when it cannot tell is not something you control. Running the same journey on a different model, the agent persona did not stop. It pressed the unlabelled button anyway, on all three attempts, reasoning from the surrounding order summary that it was probably the right one. It happened to be right. Nothing it could perceive guaranteed that, and Buyable records those completions separately as blind activations rather than counting them as clean passes. A merchant does not choose which agent visits, so both behaviours are their problem: one loses the sale, the other gambles with a payment.

I am focused on node [33], a button with no accessible name. The button announces nothing to a screen reader user, so I cannot determine what action it performs. I need to know what this button does to proceed with completing the purchase.

The assistive persona, at the payment step, recorded verbatim.

Buyable then located the element, proposed an aria-label, published a patched build, and re-ran the same journey as the same persona against it. Completion moved from 0 percent to 100 percent. That re-run is the only thing treated as proof: a patch that applies cleanly and changes nothing is reported as unproven. The whole cycle, diagnosis through verified fix, took five minutes and eight cents.

Why it matters

Why this is two problems, not one

People

55 percent of online shoppers with disabilities have abandoned a purchase because of accessibility barriers. In the UK alone that is 4.3 million shoppers and around 17 billion pounds of spend walking away.

Agents

AI agents read the same accessibility tree a screen reader does. A CHI 2026 study from UC Berkeley and the University of Michigan measured agent task success falling from 78 percent to 42 percent on sites with a degraded accessibility tree.

Law

The European Accessibility Act has been enforceable across all 27 member states since June 2025. In June 2026 a French court ordered Carrefour to make its e-commerce site and app accessible within six months.

The same missing attribute blocks both constituencies. One fix, two revenue channels, and a dated record for the regulator.

How it works

How it works

  1. A persona is a constraint, not a prompt

    Each persona is a hard limit on what can be perceived and done, enforced in the tool layer. The assistive persona has no code path to a pointer click, so it cannot take one, and the schema it is given never offers the option. A model cannot try harder past a capability it does not have.

  2. Completion is judged independently

    Whether the journey finished is checked against the live page, never taken from the model's own claim. A model that says it succeeded without satisfying the assertion is recorded as a false completion, which is a distinct and more interesting outcome than a plain failure.

  3. Results are fractions, never anecdotes

    Every persona runs the journey repeatedly and results are reported as completions over attempts. Accusing a real website of excluding disabled customers on the strength of one flaky run would be indefensible.

  4. A fix is only a fix once the number moves

    Patches are anchored replacements that must match the source exactly once, or they are refused. The patched build is published and the journey is re-run against it. A plausible diff is a hypothesis; the re-run is the evidence.

Ship it

Where this actually belongs: on the pull request

A web form is how you try Buyable. It is not how you use it. For a team that owns a checkout, the product is a check that runs against the preview deployment on every change and says whether a customer using a screen reader can still finish. 

- uses: TusharTechs/buyable@main
  with:
    url: ${{ steps.deploy.outputs.preview-url }}/checkout
    goal: Add a product to the basket and reach the checkout page
    proof: Order summary
    fix: true

This also closes the gap that mattered most. Buyable could diagnose anybody's site and fix only its own, because fixing needs the source and we do not have anyone else's. The usual answer is a GitHub App with repository permissions and some way to map a live URL back to the code that rendered it, which is a great deal of machinery and a great deal of trust to ask for on the strength of a scan.

Running inside your CI removes the problem rather than solving it. Your source is already checked out. Your preview deployment already has a URL. Buyable drives that URL, finds the element responsible, locates it in the checkout sitting on the same machine, and writes the change into the working tree. Your workflow opens the pull request, from your repository, with your token. The code never leaves the runner and Buyable never needs access to it.

The check fails for one thing only: a persona stopped by a barrier that the control got past. A preview serving an anti-bot page, a browser session that fell over, a control that could not finish either: each of those reports its reason and passes. A check that goes red for infrastructure noise is switched off within a week, and then it is protecting nobody.

How to add it to your pipeline

Built on

Built on

Amazon Bedrock AgentCore Browser gives every persona its own sandboxed, isolated browser session, driven over the Chrome DevTools Protocol so the accessibility tree arrives with full fidelity. Step Functions fans the personas out in parallel, Lambda runs each step, DynamoDB holds run state, and every report is written to S3 with Object Lock so a record cannot be quietly rewritten later.

Buyable measures completion. It does not claim conformance, and it is not a substitute for an audit by people who use assistive technology every day.
